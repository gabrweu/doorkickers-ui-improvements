# CLAUDE.md

**Era's UI Improvements**: a *Door Kickers 2* mod for the trooper Customization screen, the HUD and the campaign selection screen. Its features:
- the equipment list (one big row per item) becomes a dense, grouped icon grid, for every slot;
- slots the trooper has nothing for are hidden;
- Esc/Back closes an open list or picker before the screen;
- a portrait picker, with the stock PREV/NEXT portrait arrows fixed;
- a loadouts panel left of the Customization screen: 5 saved whole loadouts (every slot) per operator and 5 per squad (team loadouts), plus the class's starting loadout;
- the trooper hover tooltip shows Support Gear 2/3 (lockpick, crowbar, halligan) with names;
- the mission action wheel (right-click on an operator) on one page: the target's actions on an outer ring around the path's;
- the campaign selection cards show which squads completed each campaign (a badge, and the squads on hover);
- our own mouse cursor, sized to the screen;
- an on/off switch for each of the above, on the mod's page of the mod loader's Native mods screen.

It's a native plugin (`dk2_eras_ui_improvements.dll`) for the dk2ml loader (`..\doorkickers-modloader`, see its CLAUDE.md) plus GUI XML files. It knows the loader only through its public headers, copied into `dk2ml\` (`dk2ml.h`, `dk2ml.hpp`; never edit them, copy newer ones from the loader's `include\`). It needs **loader 1.0 (API v1)** and uses its GUI_LOADED, FRAME and WINDOW_RESIZED events, the GUI kit and AddOption. It declares a manifest (`DK2ML_PLUGIN_MANIFEST(1, …)` in `plugin.cpp`, version from CMake's `PLUGIN_VERSION`) that the loader reads without running the DLL; init refuses a loader whose `DK2ML_API::structSize` is smaller than the header's. The portrait picker started as a separate Portrait Selector mod (superseded by this one; its history is on GitHub, gabrweu/doorkickers-portrait-selector). Its notes are in "Portrait picker" below.

## Rules
- **Never run git.** The user commits and pushes manually (Fork). When work is done, say what changed and suggest a commit message.
- **Never upload or publish anything** (GitHub releases, Steam Workshop, the in-game Mods-menu upload).
- **Never add game-derived material to the repo:** PDB dumps, disassembly, or game assets. GUI XML references stock textures *by path* only. Our own art comes from `tools\make_art.ps1` (its `Save-Tga` writes rows bottom-up, like the stock icons: a top-down image shows upside down). Disassembly goes to a scratch folder, never into the repo. **One exception:** `mod/textures/gui/dk2ml_tt_bg.tga` is Trooper Toolbox's background (art by Sly), shipped with permission, with its slot frames painted out by `tools/clean_tt_bg.py`.
- **In-game testing is done by the user.** Never launch or kill the game.

## Build, install, test
- `.\build.ps1` (VS 2022 Build Tools, CMake, Ninja). The loader headers come from `dk2ml\`.
- **Always dry-run before asking the user to test:** `.\build.ps1 -SymTest` (needs `..\doorkickers-modloader\build\symtest.exe`). It must print `plugin init returned 0` and exit 0 (`build.ps1` stops otherwise; 100 means a call the loader would refuse). Check the logged offsets against the values below.
- `.\install.ps1` dry-runs the plugin with symtest (stops on a non-zero exit code; `-GameDir`/`-SymTest` override the paths), then copies the mod to `%LOCALAPPDATA%\KillHouseGames\DoorKickers2\mods_upload\eras_ui_improvements`, clearing that folder first so files removed from `mod\` don't linger (the game loads every `gui\*.xml`). It refuses while the game runs. `-Uninstall` removes it.
  - It also deletes the old `mods_upload\equipment_picker` dev install.
- Logs: `<game>\dk2ml.log` (plugin) and `%LOCALAPPDATA%\KillHouseGames\DoorKickers2\log.txt` (GUI XML errors).

## How it works (game build gameVersion 112)
- **Bindings** (`game.h`/`game.cpp`). Every game name is a `dk2ml.hpp` binding: `Type_member` fields, `Type_Method` functions, enumerator names, `sizeof_Type` sizes. Members of embedded structs are read at summed offsets (`dk2ml::At<T>(obj, A.Offset() + B.Offset())`). Names a game update may drop (`pTrooper`, `suppressedSwitch`, `szCaliberInfo`, the equipment-type labels in `entries.cpp`) are `dk2ml::Optional`; offsets the layout checks can rule unusable go through `UnitNameUIOffset()` / `SuppressedSwitchOffset()` / `CaliberInfoOffset()` (-1 = don't use). Hook callbacks read arguments with `dk2ml::Arg<T>(regs, n)`.
- **Events** (`plugin.cpp`).
  - `DK2ML_EVENT_GUI_LOADED`: the game rebuilt its GUI, so every module forgets its items (`Picker_`/`Grid_`/`Slots_`/`TtMerge_`/`HudTip_`/`Campaigns_`/`Loadouts_`/`Wheel_OnGuiLoaded`) and finds the new ones the next time it needs them. This replaced comparing `GuiRoot()` or cached item pointers, which a reused address could fool.
  - `DK2ML_EVENT_FRAME`: `Cursor_Tick` (does nothing unless something changed), `Picker_Tick` (the (i) buttons, see the portrait picker's Attach); `DK2ML_EVENT_WINDOW_RESIZED`: `Cursor_OnResized`.
- **The GUI kit**. `gui.cpp` keeps its interface but forwards lookups, the child walk, show/hide, AddChild/SetOrigin and Callback wiring to `dk2ml::gui::`, so the item layouts (`m_children`, `m_eventProperties`, `sAction`) live in the loader. Our Callback handlers are `(void* item, float cursorX, float cursorY, void* user)` and run crash-contained; `back.cpp` clicks with `dk2ml::gui::Click`. Rendering details (`m_size`, render objects, text colour, vtables for `IsA`) stay ours.
- **Hooks** (`plugin.cpp`, all safe hooks). Several plugins may safe-hook the same function (the loader keeps a chain per function), so sharing one with Free Camera or another mod is fine.

  | Hook | Does |
  |---|---|
  | `GameGUI::Customize_OnTrooperSelected` (pre saves `rdx`; post) | Picker refresh, then `Slots_Refresh`, `Concealment_Refresh`, then `Loadouts_Refresh` |
  | `GameGUI::Customize_OnEvent` (`edx` = event) | Pre on BACK: close the picker, or the equipment list, and skip with `rax = 1`. On CLOSED: close the picker. Post: `Loadouts_OnCustomizeEvent` (every event: the panel's marks and visibility); on OPENED attach the picker and the loadouts panel. |
  | `GameGUI::Customize_OnChangePortrait` (pre) | The fixed PREV/NEXT arrows |
  | `GUI::ItemList::Init` (post) | The equipment grid. `Init` runs for every `ItemList` in the game; we act only when `this` is `#equipment_list_parent` inside `GameGUI::m_pCustomizationScreen > #equipment_list_panel`. |
  | `GUI::Item::Show` (pre, may skip), `GUI::Item::Hide` (pre) | Keeping empty slots hidden; Show of `Menu_CampaignSelect` refreshes the campaign cards |
  | `UpdateHumanTooltip` (pre saves `rcx` and `stack[9]`; post) | The hover tooltip's support gear row (`hudtip.cpp`) |
  | `GameGUI::OpenWaypointMenu` (pre saves `rdx`, `r8`; post; optional) | The one-page action wheel (`wheel.cpp`): builds the other page and merges |
  | `GameGUI::WaypointMenu_OnEvent` (pre, `edx` = event; optional) | A CLICKED on a merged target button: that page's target id back into the menu's user data |
- **The stock list builder.** On `GUI_GAME_CUSTOMIZE_INVENTORY_SELECT` (151), `Customize_OnEvent` calls an unnamed routine (`0x140117BA0` in build 112) with the customized trooper, the clicked slot Checkbox's name, and `#equipment_list_panel`. It does five things:
  1. Deletes the old items.
  2. Collects the templates bound to the trooper's class for that slot and sorts them by `sortId`.
  3. Clones `#equipment_item_template` per item.
  4. Fills each item (`0x140115A20`): `#id` = template name, `#name`, `#image`, `#unlock` / `#unlock_stars` / `#unlock_bh_bgnd`, `#equipment_item_equipped`, `#muzzle_indicator`.
  5. Calls `ItemList::Init`, then `ItemList::ScrollTo(equipped)`.

  **EMPTY items** (the slot's "Empty" choice, from `empty.xml` binds) are filled with a null template (`0x140117EF0`): `#name` becomes `@menu_cust_item_empty`, `#id` becomes **empty**, and there's no image. Equipping that cell with its empty `#id` is how stock empties a slot. So `FromStockList` keeps such cells as EMPTY entries (the NONE group), and our cell gets the same empty `#id`. Don't skip cells with an empty `#id`.

  So in our post hook the list holds exactly the right items in the right order. `entries::FromStockList` reads them back and doesn't rebuild anything.
- **Hover and equip stay stock.** In `Customize_OnEvent`:
  - `ITEM_TRY_EQUIP` (150) calls `Customize_OnTryEquipItem(params->owner)`.
  - `HOVER_LIST_ITEM` (152) calls `Customize_OnHoverListItem(params->owner)`.

  The owner is the item whose XML `TriggerEvent` action fired; for a clone, that's the clone. Both functions go through helper `0x140117FB0`, which finds a child named **`#id`** in the item (falling back to its parent's children) and reads `StaticText::m_text` (+960) as the template name for `ObjectLibrary::GetEquipment`. **It doesn't null-check**, so every cell must have a `#id` StaticText. Our cells carry the stock item's actions and a hidden `#id`.
  - TryEquip handles the unlock cost and the `Customization_UnlockItem` pop-up. The pop-up stores the item and passes it to `Customize_OnUnlockItem` on YES.
  - Equipping hides `#equipment_list_panel` in code, which hides our grid with it.
  - `HOVER_LIST_ITEM_END` (153) doesn't use the owner.
  - We show `#equipment_details_panel` ourselves from a Callback on hover; the stock item does it from XML. That keeps our XML from naming items in `customization.xml`, which other UI mods replace.
- **Every slot.** The grid takes over every list the game builds: weapons, attachments (muzzle/scope/ammo), armor, helmets, NVG, utility pouches, support gear 1–3, and Trooper Toolbox's Custom1–9.
  - Nothing is keyed on the slot. Ammo templates have no `inventoryBinding`, and the slot Checkboxes' checked state around `INVENTORY_SELECT` / `GUI_CUSTOMIZE_UNCHECK_ALL` is murky.
  - Only empty or unreadable lists keep the stock list (`Deactivate` re-shows what we hid).
- **Grouping** (`entries.cpp`, `GroupOf`), by `EquipmentType`:
  - **Firearms** go by `category`. Stock categories come in unit flavours (`usrifle`, `opforlmg`, `militiapistol`), so they're merged by substring; unknown modded categories get their own group under the raw name in upper case. Only firearms have a category.
  - **Misfiled MGs and DMRs.** Mods file some as `rifle` (Wotan's Minimi 7.62 and SCAR 20, NGF/GOON PKMs). Before the caliber split, a RIFLES firearm with `roundsPerMagazine` ≥ 100 (`kBeltFedRounds`) goes to MACHINE GUNS, else with min(`accuracyStart`, `accuracyEnd`) ≥ 400 (`kMarksmanAccuracy`) to MARKSMAN RIFLES. Evidence across the base game and the installed mods: belt-fed guns hold 100–250, the biggest rifle magazines are 75-round RPK/AK drums; DMRs are flat 400–450 (M110A1, M14 EBR, MK20 SSR, M16A4 Marksman), ordinary rifles top out at 300 (Ranger M16A4, AUG). So the RPK stays a rifle. The values come from the template's `ModifiableParamsList` base (+0): `params` (`List<ModifiableParamsList::sValue>`, +8) → `m_list` / `m_elements`, each `sValue` (40 bytes) a `StaticString<32>` name at +0 and a float `val` at +36. `game::ModifiableParam(tmpl, name, fallback)` walks it (count capped at 256); there's no decorated `GetInt` to call. The bindings are optional and `CheckParams` (in `Resolve`) checks the layout; off means 0s and nothing moves. The one-time `caliber sample:` log line also shows `rounds=` / `accuracy=`.
  - **SMGS.** The game has no SMG category (every SMG/PDW is a `rifle`), so a firearm whose category group is RIFLES and whose caliber is pistol-calibre goes to SMGS (`SmgCaliber`). The caliber is `EqpFirearm_Template::szCaliberInfo` (char*, the XML `caliberInfoText` localization key, eg. `@firearm_caliber_9x19_name`), EqpFirearm_Template's first member at +264 (then `szOperationInfo` char*, `szEjectingShellEntity` / `szMagazineEntity` char[48], `suppressedSwitch` +376); it's optional and trusted only when 8-aligned, ≥ 264 and below a usable `suppressedSwitch` (`CaliberInfoOffset()`, else -1 and SMGs stay in RIFLES). It's read for FIREARM templates only, and the first one read is logged once (`caliber sample:`) to show it holds the XML key, not localized text. Matches: `9x19` (incl. `9x19subsonic`), `9x18`, `46x30`, `57x28`, `45acp`, `_9mm` (BV's `bv_caliber_9mm_name`). `9x39` and `.300 BLK` are rifle cartridges and stay in RIFLES.
  - **BLUFOR / REDFOR RIFLES.** The rest of RIFLES is split by the same caliber key (`RedforCaliber`): `762x39`, `545x39`, `9x39` (subsonic, AP, a raw "9x39mm"), `762x54`, `127x55`, `76239` (AKM/GP-34) and `_545` (BV's `bv_caliber_545_name`) are REDFOR RIFLES, everything else BLUFOR RIFLES. AKs in NATO calibres (Korsakov's 5.56 AK-102 / AK-102 GP-25) are Redfor by name (`AkName`: the display `#name` starts with "AK"; AK names are the same in every language). Categories can't do this: Korsakov/Wotan AKs are plain `rifle`, and the stock `militiarifle`/`afrrifle` hold FALs and M16s too. With `CaliberInfoOffset()` at -1, rifles stay one RIFLES group (no SMGS split either).
  - **Other types** use the `g_typeLabels` table: GRENADES, CHARGES, ARMOR, HELMETS, NIGHT VISION, AMMO, DISGUISES, TOOLS (lockpick, crowbar, hammer, bolt cutter, breaching kit, TEC torch). Its enum names are optional bindings resolved at init; a missing one is logged and its items fall into OTHER.
  - **`SCOPE`** is OPTICS in a slot whose binding contains "Scope", else GEAR: Trooper Toolbox's Custom slots hold cosmetics as `<Scope>` items.
  - **`EMPTY`** is NONE, a group without a header row (`Headerless` in `grid.cpp`, also never sticky): the Empty cell sits alone at the top.
  - **Order:** NONE (the slot's Empty choice) always comes first; the other groups appear in stock (sortId) order, by first appearance, and each gun group's items (every member a FIREARM) are sorted (`CaliberThenName`): by caliber size first, then by their shown (localized) `name` in natural order (`natural::Compare`, `core/natural.h`, shared with the portrait picker: case-insensitive, digit runs as numbers), `stable_sort` so equal names keep stock order. With setting `sort_by_name` off, items stay in stock order.
    - **Caliber size.** `Entry::caliberName` is `Loca::GetTextForId` of the raw `szCaliberInfo` key (looked up before lower-casing: the lookup may be case-sensitive, eg. `9x39AP`; empty if it fails). `CaliberSize` parses it: `NxM` = bore N mm, case length M (the first round of `5.56x45mm/40mm HE`); a leading `.` = inches × 25.4 (`.45 ACP` 11.4); `40mm` / `84mm HEAT` = bore only; `12 Gauge` = kind 1 (after bullets); no number = kind 2 (last). `.` or `,` decimal marks. Bores are rounded to 0.1 mm, so `.300 BLK` sits with 7.62 and `.38`/`.380` together. Order: kind, bore, case length, caliber name (natural; keeps `9x19mm` / `9x19mm Subsonic` apart, GL variants after the plain round), item name. Other groups (armor, grenades, cosmetics, ammo, a mixed OTHER) keep stock order. A parsed sample is logged once (`caliber size sample:`).
- **Squadmates' gear** (`entries::MarkSquadUse`, setting `squad_usage`). When a list is built, every inventory slot of the other troopers in the customized trooper's **own squad** is read (`Roster::Trooper::inventory` names) through `portraits::Squadmates`, which shares the portrait picker's validated roster walk (`ReadRoster`). An entry whose template name a squadmate has in any slot gets `usedBy` (their names). Its cell shows `#dk2ml_ep_cell_used` (a light 16% tint + tag), and hovering it shows `#dk2ml_ep_usedby` beside the cell.
  - **The pop-up** (`ShowUsedBy`) is built top-down: the item's icon (`#dk2ml_ep_usedby_img`, not aligned, fitted into 200×64 at most scale 0.6; hidden without an icon), the title "USED BY N OPERATOR(S)", then the names (`usedBy` is a list of names). Its height is fitted to the names: `ChangeText` with `sizeX` and no `sizeY` leaves the wrapped height in `m_size.y`; the pop-up's `m_size.y` is set and the two named backgrounds are stretched in y (render scale). Then the children are re-placed with SetOrigin. Names that would make it taller than the grid become "+N MORE"; the title count stays complete. The names placeholder is ~700 characters (`ChangeText` caps at the XML length).
  - The pop-up goes on the side with more room and never over the hovered cell, which would end the hover; it's clamped vertically to the grid.
  - It hides on hover end (an `OnHoverEnd` Callback in both templates), scrolling, and deactivation.
  - Empty entries never count.
  - **Suppressed weapons.** A suppressor isn't an attachment: the muzzle list holds suppressed firearm twins (eg. `FRWD_CSAW_Sup`, `inventoryBinding="PrimaryWeaponMuzzle"`), and equipping one replaces the trooper's `PrimaryWeapon` name. `EqpFirearm_Template::suppressedSwitch` (+376, char*) links the twins. A squadmate with a muzzle-bound twin also counts for the plain weapon (`SuppressedTwinOf`), not the reverse. Ammo has separate `_Sup` variants with no link, so ammo counts stay split.
- **Layouts** (`g_layouts` in `grid.cpp`, picked by `LayoutFor`), each with its own template and lazily cloned cell pool; the header pool is shared:
  - **Wide cells** (`#dk2ml_ep_cell_template`, 268×146, 2 columns, 6 rows, icon box 256×78, max icon scale 0.75). Used when more than half the list is firearms (`List::wide`): weapon and muzzle lists, whose icons are about 360×112.
  - **Square tiles** (`#dk2ml_ep_tile_template`, 176×148, 3 columns, 6 rows, icon box 164×80, max scale 0.8) for everything else. Those icons are 50–270 px and roughly square: armor 272×188, grenades 120×144, cosmetics 128×128.
  - **Weapons per row** (setting `weapon_columns`, a CHOICE: 2 / 3 / 4, default 2). Weapon (`List::wide`) lists use the wide cells at 2, and icon-only cells at 3 (`#dk2ml_ep_cell3_template`, 176×84, icon box 164×64) and 4 (`#dk2ml_ep_cell4_template`, 128×60, icon box 120×48, lock ribbon / equipped mark at scale 0.5). The icon-only templates have no `#dk2ml_ep_cell_name` (`FillCell` skips a missing one; the details panel shows the name on hover) and a centred icon box. Columns follow from their widths. Other lists always use the tiles.
  - All templates have the same child names (the icon-only ones minus the name), so `FillCell` works with any. Only the wide template is required: a missing one falls back to it.
  - Switching layout hides the other layout's cells.
- **Trooper Toolbox** (workshop 3299377664, which replaces `customization.xml`):
  - It keeps `#equipment_list_panel` / `#equipment_list_parent`. It nests `#id` inside `#sortid`, and both `gui::Find` and the game's helper are recursive.
  - Its extra slot Checkboxes (`Custom1..9`, `SupportGear2/3`) open the same list, so the same hook covers them.
  - Its list origin is `55 124` (see Attach).
- **Trooper Toolbox merge** (`ttmerge.cpp`, setting `tt_main_page`). TT's `#cosmetic_panel` (Custom7–9, SupportGear2/3, `#close_cosmetic_panel`) is a child of `#inventory_panel`, both `align="r"` with no origin, so it shares the main page's coordinate space. Nothing is copied or reparented:
  - **Geometry**, once per GUI on the first trooper select / OPENED with TT found:
    - the five Checkboxes get main-page origins (`kPlaces`, fitted on a 2000×1125 screenshot: `x = -544 + (left − 1022) × 1.28`, `y = 528 − (top − 88) × 1.285`);
    - they're resized to Custom3: its `m_size` (Checkbox and both `m_pButtons`), each of the 3 render objects per Button scaled to Custom3's drawn size (size × scale), and `#image` scale/origin and `#name` origin copied;
    - the originals are saved and restored when the setting goes off.
  - **Layout:** Custom7 / Custom9 over the shoulders (mirrored), Custom8 under Custom6, SupportGear2/3 after UtilityPouch2 on the pouch row (the equipment row below would put their labels off the window). Places have a group: SupportGear2/3 share theirs, and `TtMerge_Arrange` (after `Slots_Refresh` and `Slots_SetEnabled`) gives the visible ones the places in order, so a slot hidden by slots.cpp leaves no gap.
  - **Icons** are fitted with `gui::FitImage` into the reference box's drawn size × 0.85 / 0.7, at most the reference icon's scale (0.6), after each trooper select and whenever `#inventory_panel` is shown again (`TtMerge_OnShow`: TT's `SHOW_DEFAULT` after a list closes).
  - **Visibility**, in the `Item::Show/Hide` hooks (`TtMerge_SkipShow/SkipHide`, checked after `Slots_IsInternal` so the empty-slot hiding still works): skip Show of `#cosmetic_panel_toggle` / `#close_cosmetic_panel` and Hide of `#cosmetic_panel` and the five slots. A slot click hides `#inventory_panel`, which hides them with it. Re-asserted on every trooper select (before `Slots_Refresh`).
  - **Credits** (`gui/tt_credits.xml`). TT's credits are baked into its second page's background (`customization_menu_bg_b.tga`), unseen while merged. Our `#dk2ml_tt_credits` Button (`align="r" origin="-345 -635"`, the spot of TT's `#cosmetic_panel_toggle` in `#inventory_panel`) is moved into `#inventory_panel` with AddChild on the first merge, shown by `ShowMerged` and hidden when the setting goes off. Its pop-up `#dk2ml_tt_credits_popup` (StaticImages/StaticTexts only, fixed text transcribed from the image, author Sly from TT's `mod.xml`) is shown/hidden by plain XML Show/Hide actions on the button's OnHover/OnHoverEnd. Optional: without the XML item, the merge logs it and goes on.
  - **Background and frames** (`ttbg.cpp`, `gui/tt_background.xml`, called from `TtMerge_Apply` after the geometry). TT paints its main page's slot frames into its background (`customization_menu_bg.tga`, 1451×1340 drawn at 1400×1401, colour `ffffffc0`, the StaticImage child of `customization_bg_image`). The slot textures (`small_button_nobar_*`, `small_button_normal`, `large_button_normal`) are frameless translucent fills with a 4 px transparent border. So a slot hidden by slots.cpp left an empty frame, and the merged slots had none.
    - **The swap.** Our `#dk2ml_tt_bg` (`dk2ml_tt_bg.tga`: TT's own background with its frames painted out, in TT's own format, uncompressed 32-bit, rows bottom-up, 1451×1340 drawn at 1400×1401, same colour, `stealFocus` like TT's) is moved into `customization_bg_image` with AddChild, and TT's image is hidden. TT's own Show/Hide of that item (a black background while a list is open) applies to both. `TtBg_SkipShow` (in `TtMerge_SkipShow`) keeps TT's image hidden if a Show reaches it.
    - **Frames.** Each slot in `kFramed` (TT's main-page slots plus the merged five) gets a clone of `#dk2ml_tt_frame` (`_dark` for Armor, which sits on the figure's cream plate carrier) as its last child, once per GUI. - **The grid is virtualized** the way the portrait picker's is: rows are group headers or up to the layout's `cols` cells, and only one screen of slots is cloned per layout (`EnsureHeaders` / `EnsureCells`, once per GUI load).

  - **Scroll stops** (`src/core/scroll.h`, shared with the portrait picker). A top on a group's header looks exactly like a top on its first card row (the header sticks), so headers aren't stops: `scroll::Stop` moves a header top to the next row, and `scroll::Step` counts card rows only.   - **Measuring text.** `StaticText::ChangeText` lays the text out right away (`StaticText::UpdateRenderObject`, `0x1400DFBD0` in build 112), with word wrap at the hardcoded width.
    - For each axis without a hardcoded size (`m_hardcodedSize` +0x3B0/+0x3B4, from the XML `sizeX`/`sizeY`), it writes the laid-out text's size into `Item::m_size`.

    2. It sets the name and keeps it if it fits in two lines.
    3. Otherwise it drops words from the end (then characters) with "..." until it fits.

    The full name is in the details panel on hover.

  - **What the game does.** `StaticImage::SetImageAndImplicitSize` writes the texture id, the texture's pixel size and `bNeedsUpdate` into the image's inline `RenderObject2D` (`m_renderObject`). ## Loadouts panel (`loadouts/store.cpp`, `loadouts/panel.cpp`, `gui/loadout_panel.xml`, setting `loadout_tabs`)
Left of the Customization screen: MY LOADOUTS (the operator's own) and TEAM LOADOUTS (the squad's, shared by every squadmate), 5 rows each (`kProfiles`), and after MY LOADOUTS' rows the class's **starting loadout** (see below). Each is a profile (`loadouts::Profile`): the whole loadout, every slot. Clicking a row equips all of it; its SAVE button stores everything the operator has equipped now, overwriting at once. The UI calls profiles "loadouts" ("Loaded team loadout 2"). (History: before this there were 4 per category (GUNS / GEAR / LOOKS), each loading only its category; before that, per-category tab strips with auto-save, which never found room on Trooper Toolbox's screen: its equipment stats panel sits above the weapon column and pouch row, and the stars / battle-honors ribbons (`rt 110 30` in TT, `rt 218 30` / `218 -190` stock) take the right margin.)
- **Categories** (`g_slots` in `store.cpp`, optional `Inventory::eType` enumerator bindings, logged at init as `loadouts: GUNS = ...`). Internal only now: undo (history.cpp) diffs, labels and writes per category, and the rows' summaries are per category. `Read` / `Write` take a category or `kAll` (every slot), which the panel uses:
  - GUNS: PRIMARY_WEAPON + _SCOPE/_AMMO/_MUZZLE, SECONDARY_WEAPON + its three, MOUNTED_GUN;
  - GEAR: UTILITY_POUCH1/2, SUPPORT_GEAR1-3;
  - LOOKS: HELMET, HELMET_NVG, ARMOR, CUSTOM1-9.

  Each slot that depends on another stays with it (attachments and suppressed `_Sup` twins with their weapon, NVG with the helmet), so a loadout is always written back as one consistent set. `parent` in the table is that slot's index.
- **Writing a slot** is what the game's Paste loadout does (`Customize_OnPasteLoadout`, its per-slot copy at `0x140118FB0` in build 112): the name into `StaticString<48>::m_szString` (47 chars max) and `m_hash` = FNV-1a of it, 0 for empty (`EquipItemToInventory`, `0x1401141F0`, writes the same). Paste checks the weapon/helmet with the bind rule (`0x140112B40`, `game::BoundToTrooper`, shared with `slots.cpp`) and copies the attachments/NVG with it unchecked; so does `Write`. A template that's gone or not bound to this operator is skipped and logged, its whole group with it, and counted (`WriteResult::skipped`, shown in the status line): that's how a team loadout saved by another class loads. Unlock costs aren't checked: loadouts hold items someone in the squad has equipped. After a change, `game::SaveAndRefresh` (shared with the portrait picker) runs `Roster::Save`, `Customize_OnTrooperSelected` and `Deploy_Update`.
- **Storage.** `GetConfigDir()` + `loadouts.ini`: a block per set, `[squad|name]` for an operator, `[team:squad]` for a squad, and a line per saved profile: `profile2<TAB>~name=Stealth<TAB>PrimaryWeapon=NAME<TAB>...` (`~name` optional; a named profile nothing was saved in has a line with only the name) (slots by `Inventory::GetNameForEnum` name, so the enum order doesn't matter; a slot missing from a profile is left alone). Lines with another head (the per-category version's `guns2` / `gear2` / `looks2`, the tab version's `active=`) are ignored, so the next save drops them (the user chose not to migrate them). ## One-page action wheel (`hud/wheel.cpp`, `gui/action_wheel.xml`, setting `one_page_wheel`)
Right-clicking a trooper or a waypoint opens `#waypoint_menu` (the game's `data/gui/waypoints.xml`), built by `GameGUI::OpenWaypointMenu(const ActionWP_Client* wp, eOpenWaypointsType)` (from `GameInput::Button2_Click`, `GameGUI::Profiles_Clicked`, and the "more" buttons). With a target nearby it has two pages; the user wanted one. The path page stays on the inner ring as stock; the target page goes on an outer ring (the user's choice).
- **Open types** (`GameGUI::eOpenWaypointsType`): DEFAULT 0 (the wp's own target, `wp+0x1f4`; none = the path page), TARGETED 1 (`ActionWP_Client::CheckForSurroundingTargets` + `GetDefaultAction`), PATH 2 (no target). The "more" buttons, `#switch_to_path_options` (shown on a target page) / `#switch_to_target_options` (on the path page when a target is around), both at `0 256`, raise `GUI_GAME_WAYPOINT_OPEN_PATH_OPTIONS` (83) / `_TARGET_OPTIONS` (82); `WaypointMenu_OnEvent` then does `menu->Hide()` and `OpenWaypointMenu(wp, 2 | 1)`.
- **A build** (`0x1400FD3F0` in build 112):
  - deletes every child of `#menu_parent`; hides `#menu_static_buttons`' children (recursively) and `#go_silent` / `#always_wait` / `#speed_sync`;
  - clones a Button per action from `#action_template` (helper `0x1400FB4B0`) into two arrays: ring 0, general (target helpers `0x1400FBD00` doors, `0x1400FCB40` humans, `0x1400FD210` windows / drapes; path helpers `0x1400FC020` / `0x1400FC9A0`), ring 1, equipment (`0x1400FB7A0`); static buttons (`delete_path`, `delete_waypoint`) from `#menu_static_buttons` go in too;
  - lays both out on one circle: radius = `#menu_ring`'s texture width (256) x 0.73 = 187, step = the IGNORE action's button texture width (120) / radius (~37 degrees, ~9.8 slots in all), ring 0 centred at 90 degrees (top, +y up), ring 1 at 270, angle_i = centre + step/2 - n*step/2 + i*step; AddChilds parentless buttons into `#menu_parent` and Shows each;
  - the go-codes row (`#gocodes_parent`, Checkboxes 40 apart) for a player trooper; shows the right "more" button;
  - stores the target id in a static and the menu's user data;
  - places the menu at the waypoint (`ConvertMapToScreenCoords`, relative to the GUI's centre, from `GUIManager::m_width/m_height` and the viewport), moves it last in its parent and Shows it.
- **`Item::Show` / `Hide`** do nothing on an item already shown / hidden. Hide runs EVENT_CLOSE (the menu's OnClose: `GUI_GAME_WAYPOINT_CLOSE`, which unpauses and may clear an action-less waypoint), Show EVENT_OPEN (`GUI_GAME_PAUSE`). So we rebuild without hiding: the menu stays shown and nothing fires twice.
- **A click.** The button helper writes the action type and inventory slot into the clone's TriggerEvent actions (sAction `+0x40` / `+0x44`), so `GUI_GAME_WAYPOINT_CLICKED` (73) arrives with `GUI::sEventParams {owner +0, cursor +8, iParam1 +16 type, iParam2 +20 slot}`. The handler reads the target from the menu's user data (`GUI::Item::m_userData` +848, `GUI::sUserData {void* ptr; unsigned id}`: `ptr` points at the game's static target id, `id` = the waypoint's entity id) and calls `ActionWP_Client::OnChangeAction(type, slot, *ptr)`, then `RequestActionWaypointCreation` for `ActionWP_Client::s_potential`. The path page stores 0.
- **The merge** (`Wheel_OnOpened`, the post hook of a call that isn't ours; `g_building` guards our own):
  1. `#switch_to_path_options` shown: the target page is up. `#switch_to_target_options` shown: build TARGETED first. Neither: the stock wheel.
  2. Read the target id; move every `#menu_parent` child into our hidden top-level `#dk2ml_wm_hold`, noting its origin and whether its `#hover_eqp` is shown (the helper shows it on buttons made for an equipment item, else `#hover_general`).
  3. Build PATH, last, so the static buttons, go-codes and toggles end as stock has them.
  4. Move the kept buttons back into `#menu_parent` (the game deletes them on the next open, as its own) and lay them out the game's way at radius inner + 128 (inner = the farthest path button, else 187): equipment centred at the bottom, the rest at the top, each arc in the game's order (by angle around its centre). Hide both "more" buttons.
  5. Show `#dk2ml_wm_outer` (our own ring and a 760x760 stealFocus click catcher). The ring is `dk2ml_wm_ring.tga` from `tools/make_art.ps1`: one dotted line (the user's choice, after a dashed one matched to the stock ring's): round dots 4.5 units across, ~12 apart (the stock dotted line has ~3 px dots ~2.5 apart; its dashed line, measured from `action_menu_rings.dds`: radius 180, 7 inside its buttons, ~5 thick, 11.3 dashes / 4.5 gaps, `ffe3ce` at 50%), at radius 308 (the outer buttons' 315 - 7, where stock has its dashed line), one 640x640 quarter at 2x (scale 0.5, sharp at high resolutions) flipped into four, with 40 dots a quarter and half a spacing at each end so the quarters meet evenly. It's fixed art: an inner radius other than the stock 187 would leave it a few px off the buttons.
  7. **The inner ring** (`UseOurInnerRing`, on every top-level open, merged or not): while the setting is on, the stock ring's images are hidden and `#dk2ml_wm_inner` shown: `dk2ml_wm_ring_inner.tga` (same `Draw-RingQuarter`, radius 180 like the stock dashed line, 368x368 quarter, 24 dots a quarter). The stock images are `#menu_ring` and the `#waypoint_menu` StaticImage child with the same texture id (`RenderObject2D::texture` +8 of `m_renderObject`; optional binding), its unnamed flipped half; found in `PlaceRings`, which also puts `#dk2ml_wm_outer` then `#dk2ml_wm_inner` right after the stock ring's images among `#waypoint_menu`'s children, where the stock ring is drawn: over the stock shadows (two `action_menu_shadow.dds` images, `multiply_inverse`, over the middle 640x640; placed first, our rings were darkened by them, the inner one most, and the two rings looked different) and under everything else. The stock 360 catcher, portrait and buttons come after, so they're still hit-tested before the outer catcher; without the stock ring, our rings go first, once per GUI. The game never shows/hides them (it only reads `#menu_ring`'s texture size for the radius). Setting off: shown again, ours hidden. Both rings are tinted `a39a8c` at 60% alpha (`a39a8c99`; stock is `ffffff7f`), a bit darker so the buttons stand out. Once per GUI (`PlaceRings`, see 7) the menu's children are AddChild-ed again in order, with our rings inserted right after the stock ring's images.
  6. Clamp the menu's origin so the outer ring (+ half a button) stays inside `GUIManager::m_width/m_height` (the menu has no align flags).
- **Both equipment arcs stay, paired** (`InnerTwins`, `PairedArc`, `AddBadge`). Both pages have an equipment arc: the path page's uses the item with no target (thrown at a spot), the target page's uses it on the target (`0x1400FB7A0` asks the target per item, vtable +0x68, so some are greyed out there). They behave differently in game, so both stay (hiding the inner copies was tried and dropped: it lost the thrown-at-a-spot version). After the PATH build, the inner bottom arc's visible equipment buttons (y < 0, `#hover_eqp` shown; only equipment is there) give slot -> angle. On the outer bottom arc, a kept equipment button with the same slot goes at its twin's angle (inner buttons are ~37 degrees apart, ~200 px on the outer ring, so twins never collide) and gets a clone of `#dk2ml_wm_badge` (`dk2ml_wm_door.tga` from `tools/make_art.ps1`: the wheel's door-opening icon redrawn by us with an orange arrow, as the user asked; the stock `door_open_normal.dds` can't be recoloured: no game art in the repo, and an XML `color` only multiplies, so its blue arrow can't turn orange; 48 px at 0.75, at `40 40`: top right; `#quantity` is bottom right) made like the campaign badges (`StaticImage::CloneInternal`, `UpdatePointerReferences`, `SetName(nullptr)`, AddChild into the button: the game deletes it with the button). The others keep the game's order at the outer step (120 / R2): those before the first twinned one to its left, the rest after the rightmost twin (angles grow left to right along the bottom). No twin: the centred `Arc`. No template or no `CloneInternal`: logged once, no badges.
  - **A button's slot** (`SlotOf`): the button helper writes the action type and slot into each click action whose `eventId` is GUI_GAME_WAYPOINT_CLICKED (`eventParams.iParam1` / `iParam2`). The click actions: `GUI::Item::m_eventProperties` (+168) is `GUI::Item::sItemEventProperties[]` (stride 48) by `eItemEventType`; `[EVENT_CLICK].actions` (+0) is a `List<GUI::sAction *>` (`m_list` +8, `m_elements` +16, so +272 / +280 as the helper reads them); `GUI::sAction::eventId` +40, `eventParams` +48 (`iParam1` +16, `iParam2` +20). Optional (`game::WheelButtonSlotsUsable()`, logged as `offsets (action wheel buttons):`); without it nothing is paired (the centred arcs). The slot is the key, not the action type, which could differ between pages.
- **Repeated general actions** (`HideRepeats`). The human-target builder (`0x1400FCB40`) falls back to the path page's general-actions helper (`0x1400FC020`, the call at `0x1400FCF21`) when the human isn't a usable target (its state isn't 2/3 and the flag at +0x332 is off, or it's too far), so that target page's top arc is the path page's stance / speed / check corners again. After the PATH build, an outer general button whose click (`ClickOf`: `iParam1` action type +16, `iParam2` slot +20, of its GUI_GAME_WAYPOINT_CLICKED action) equals a shown inner button's is hidden and left out of the top arc; the inner copy (path page, target 0) stays. Hidden ones still go back into `#menu_parent` (the game deletes them). Equipment is never dropped (see the pairing above). No target button left: the plain path page. Counted in the one-time merge log line (`N repeats of path actions hidden`).
- **Clicks on the outer ring** (`Wheel_OnEvent`, the `WaypointMenu_OnEvent` pre hook): a CLICKED whose `owner` is one of the kept buttons (compared, never dereferenced; the list is cleared on each open and on GUI_LOADED) writes the target page's id into `*m_userData.ptr` first. Path buttons get the PATH build's value, as stock.
- Other plugins' `OpenWaypointMenu` hooks run once per build (Visible Lasers re-adds its two per-trooper buttons into `#waypoint_menu`, idempotent).
- **Bindings**, all optional (`game::WheelUsable()`: names resolved, `m_pWaypointMenu` and `m_userData` 8-aligned, `sUserData::ptr` and `sEventParams::owner` at 0; else logged and not hooked). Expected: `GameGUI::m_pWaypointMenu` 8 (the PDB's 32-bit copy: 4), `GUI::Item::m_userData` 848 (556), `GUIManager::m_width/m_height` 16/20, `OPEN_WAYPOINTS_TARGETED/PATH` 1/2, `GUI_GAME_WAYPOINT_CLICKED` 73. Logged as `offsets (action wheel):`; the first merge per GUI logs `action wheel: one page (...; N paired with their inner twin)`.
- Not covered by testing so far: coop (OnChangeAction sends the net events itself), a `waypoints.xml` replaced by a UI mod (none installed; every name is the stock one, a missing one means no merge).

## Campaign cards (`campaigns/cards.cpp`, `gui/campaign_cards.xml`, setting `campaign_cards`)
The campaign selection screen (`Menu_CampaignSelect`, stock `campaign.xml`; no installed mod replaces it).
- **The cards.** `GameGUI::Campaign_Init` builds them once (from `GameGUI::Init`, and after a progress/history reset), not on every open.
  - For each `CampaignDef*` in `g_campaignDefs`, it clones `#CampaignSelect_ItemTemplate` (530×808; the drawn card is 504 wide) into `#CampaignSelect_List` (an ItemList, `direction="x"`) and **names the card after `CampaignDef::fileName`**. `Campaign_UpdateLockStatus` finds cards the same way.
  - Card layout, from the bottom: a 496×80 band with `#type`/`#name` (left-aligned; `align="b" origin="0 4"`). From the top: `#continue`'s 228 px banner (`origin="0 -4"`), shown only with a run in progress. The middle is thumbnail art.
  - `#campaign_hover` is a child of the card item, before the Button. The Button's XML OnHover/OnHoverEnd show and hide it, so whatever we put inside it shows exactly while the card is hovered.
  - The per-card refresh is the module-local `UpdateCampaignSelectItemVisuals(card, def)` (`0x140108140`): `#continue`, unit banner, squad name, thumbnail. It doesn't touch our children.
- **The data.** `g_campaignHistory` is a module-local `List<CampaignHistory>`: not in the publics, but resolved by name.
  - `CampaignManager::End` appends one entry per finished run (newest last), then saves `campaign_history.xml`. It doesn't refresh any card.
  - An entry has `fileName` (char[128]) and `squadName` (char[32], `Roster::Squad::name` when the run ended; there's no squad id). `flags` is `CampaignProgress::eCampaignProgressFlags`: IRON_MAN 1, COMPLETED 4 (every history entry), COMPLETED_FAIL 8 (only the debug "finish lose" sets it).
  - The user chose: every history entry counts.
- **When.** On every Show of `Menu_CampaignSelect` (the `Item::Show` pre hook). That covers the first open and returning after a finished campaign. The screen, the list and our templates are found in `Campaigns_OnGuiLoaded`; nothing is looked up before the first GUI_LOADED.
  - There's no `Campaign_Init` hook: it can run during a GUI reload, before GUI_LOADED, when a cached screen pointer would already be freed.
- **Per card.** Cards are matched by name to the history's `fileName` (case-insensitive, either slash). Our clones are found again inside each card by name (`#dk2ml_cc_badge`, `#dk2ml_cc_list`), so nothing is kept per card, and a card the game deletes takes them with it.
  - **Cloning.** Clones are made with `GUI::StaticImage::CloneInternal` + `Item::UpdatePointerReferences` + `SetName`, then AddChild. Both templates are StaticImages, and so are all their children: they never take the cursor, so the card keeps its hover, preview movie and click.
  - **The badge** is the card's last child (drawn on top), bottom right, above the band. It shows the medal (`CampaignManager::GetDef(fileName)->medalImage`, fitted into 100×32, hidden when empty) and "COMPLETED" / "COMPLETED xN". Its width is fitted: a StaticText with no `sizeX` gets its laid-out width in `m_size.x`. The chip is stretched (`gui::StretchTo`) and its `m_size` set, and the `align="r"` text is re-placed.
  - **The list** goes into `#campaign_hover`, from just above the badge up to at most below the CONTINUE banner. It has one line per squad (most recent run first, " xN" for repeat runs) and "+N MORE" when it doesn't fit. Its height is measured like the grid's "used by" pop-up (`gui::SetTextMeasured`).
- **Bindings.** Everything is `dk2ml::Optional`. `game::CampaignCardsUsable()` is false (logged) if a name is missing or the layout looks like the PDB's 32-bit copy; the rest of the plugin works without it.

## Portrait picker (`picker.cpp`, `portraits.cpp`, `gui/portrait_selector.xml`)
Brought over from the former Portrait Selector mod; item names keep its `#dk2ml_ps_` prefix. Its hooks are in the table above.
- **Clicks.** Our XML uses `<Action type="Callback" target="...">`. `sAction::Execute` calls `pCallback(const sAction&)` when it's non-null. `gui::SetCallback` has the loader point it at our handler (`GuiSetCallback`: a thunk into a crash-contained call), for our own actions only. The XML loader requires a target that exists.
- **Cloning.** `Item::CloneInternal` is a deep copy: it clones the children and the actions. `CloneActions` copies `pCallback` and sets `owner` = clone, so a cell's handler gets its cell as `item` (the loader reads `action.owner`).
- **Hit-testing** (`GUIManager::FindItemUnderCursor_Recursive`): hidden items are skipped, and children are tested last to first, before their parent. A `stealFocus` item under the cursor returns **itself**, and its children are never tested. So a `stealFocus` background must be an earlier sibling of the controls, never their parent, as in the stock screens.
- **Attach.** Customization_Screen captures input, so the picker must be its child. The open button goes on `#player_profile_panel > #portrait` (other screens have a `#portrait` too), at its bottom left (`lb 73 106`). Re-adding the picker with AddChild on open puts it last, which makes it topmost for drawing and hit-testing.
  - **The (i) moves down beside it** (`MoveInfoButtons`). The stock (i) (STATS on hover) is an unnamed Button, `align="lt" origin="15 -15"`, a direct child of `#portrait` (stock and Trooper Toolbox's `customization.xml`). It's found as the unnamed `GUI::Button` child with the same `m_alignFlags` as its pop-up sibling `#player_profile_info` (also `lt`; the PREV/NEXT arrows are `l` / `r`). Unit History's clickable twin `#dk2ml_uh_info` (same place) is found by name.
  - Each is moved with `gui::ShiftBy` so its bottom edge is `kInfoBottom` (106, the open button's XML y) above the portrait's: dy = −(portrait `m_size.y` − 106 − item `m_size.y` + its XML origin y (`m_alignOffset.y` minus what we applied)), −295 for the stock one. `g_infoShift` tracks the applied dy per item (cleared on GUI_LOADED), so it's idempotent; with the `portraits` switch off the wanted dy is 0 and they go back.
  - It runs in `Picker_Attach` and every frame (`Picker_Tick` on the FRAME event, a walk of `#portrait`'s ~8 direct children), because Unit History attaches its twin from its own `GUI_GAME_CUSTOMIZE_OPENED` subscription, before or after ours.
- **The list is virtualized.** The content is a list of rows (`BuildRows`), each either a group header or up to `cols` entries of one group. Only one screen of row slots exists.
  - **Building the slots.** The first time the picker opens (and again after a GUI reload), `cols × visibleRows` cells and one header per slot are cloned into `#dk2ml_ps_grid`, a plain Item. The counts are `floor(grid / (cell + gap))` per axis, so 10 × 11 at the current sizes. Each one is built the way the stock equipment list builds its items:
    1. `Button::CloneInternal(template)` (`Item::CloneInternal` for headers)
    2. `UpdatePointerReferences(clone, clone, root)`
    3. `SetName(clone, nullptr)`
    4. AddChild into the grid
    5. `SetOrigin`: relative to the grid center, +y up
  - **Scrolling** moves a window `[g_top, g_top + visibleRows)` over the rows and re-skins the slots: `StaticImage::SetImageAndImplicitSize`, the current-portrait and squadmate marks, and Show/Hide. A cell that already shows the right entry is skipped unless forced. A huge mod pool therefore costs one screen, not thousands of GUI items.
  - It scrolls in **whole rows**, because nothing clips a partly visible row.
  - Cells are never deleted. That matters because `ExecuteOnEvent` and `OnCursorUp` keep using an item after its action runs, so an item must never be deleted inside its own event. Scrolling inside a cell's own scroll event is safe for the same reason.
- **Input.**
  - Mouse wheel: Callbacks on `EVENT_SCROLL_DOWN`/`EVENT_SCROLL_UP` on the cells, headers, grid and scrollbar scroll 2 card rows per notch (`scroll::Step`, see the grid's scroll stops).
  - Scrollbar: `#dk2ml_ps_thumb` (a child of `#dk2ml_ps_track`) uses `EVENT_CURSOR_DOWN` and `EVENT_DRAG` Callbacks.
  - `Item::ExecuteOnEvent` stores `{owner, cursor}` in `sAction::eventParams` before running an action. The cursor is in the GUI's +y-up space, so the drag maps the cursor delta since the press onto rows. No screen mapping is needed.
  - Header text is set with `StaticText::ChangeText`. It copies the text but caps it at the item's length limit from the XML, so the XML placeholder must be at least as long as any label.
- **Grouping by unit** ("All units"). `sHumanPortrait::unit` is only the hash of the unit name, which is also its `StaticString<48>::m_hash`.
  - `ObjectLibrary::GetUnit(const StaticString<48>&)` compares only `m_hash`. A zeroed key with just the hash set therefore finds the `ArmyOrg::Unit`. That avoids reading `ObjectLibrary::m_units`, whose offset differs between the PDB's layouts.
  - Header text is `Loca::GetTextForId(unit.nameUI)`, upper-cased, falling back to `unit.name`. The PDB also has a 32-bit `ArmyOrg::Unit` layout (`nameUI` @52); `game.cpp` rejects a `nameUI` offset that isn't 8-aligned.
  - Group order: the trooper's unit, then other units by internal name, then OTHER PORTRAITS (hashes with no unit, e.g. a mod's private pool). Within a group, entries are sorted by file name in natural order (`NaturalLess`, on `natural::Compare`: case-insensitive, digit runs as numbers, so ranger2 comes before ranger10), for both filters.
  - Every group starts a new row, under its header (see the virtualized list above). `g_cellEntry` maps each visible cell to the entry it shows.
- **Applying a portrait** mirrors `Customize_OnChangePortrait`:
  1. Copy `tex` into `trooper.id.tex` and copy `gender`. Leave `texHash` alone; stock doesn't touch it.
  2. `Roster::Save()`.
  3. `Customize_OnTrooperSelected(trooper)` for the profile refresh (it builds the `_large` texture name itself).
  4. `Deploy_Update` with `m_deploySelection.roster.pTrooper` temporarily set to the trooper.
- **Hover pop-up** (`#dk2ml_ps_preview`): the cell template's `OnHover`/`OnHoverEnd` Callbacks (`EVENT_CURSOR_HOVER`/`_END`, owner = the cell) show and hide it. It shows the large portrait, the file name and "Used by NAME".
  - The pop-up is moved into the grid after the cells are cloned, so it draws above them and shares their coordinates. It's placed beside the hovered cell, never over it (covering the cell would end the hover). It re-renders when scrolling changes what the hovered cell shows.
  - **Large portrait:** `tex` with `_large` inserted before the extension, as the game builds it for the Customization screen.
  - **Layout:** the pop-up is 360×470 and top-anchored. "Used by" is a `sizeX` + `wordWrap` StaticText, the same attributes stock `campaign.xml` uses, so a long list wraps downwards. A CURRENT badge (`#dk2ml_ps_preview_current`) marks the trooper's own portrait.
  - **Missing `_large` fallback:** when there is no `_large` version, the pop-up shows the cell texture in `#dk2ml_ps_preview_img_small` (scale 3) instead.
    - Existence is checked with `FileManagerImpl::FileExists(*g_fileManager, path)`. It goes through `SearchFileInDataFolders`: game data, packed archives and mods.
    - The result is cached per path.
  - **Size:** `StaticImage::SetImageAndImplicitSize` replaces the `RenderObject2D` texture (+8) and `size` (+68) but keeps `scale` (+60), so the XML `scaleX`/`scaleY` (0.6) still apply.
- **Roster-wide usage** (`portraits::UsedInRoster`): walks `Roster::m_squads` (`List<Roster::Squad *>`), with each squad's inline trooper array validated as below.
  - Squadmates' portraits get the strong dim (`#dk2ml_ps_cell_used`); portraits worn only in other squads get the light one (`_used_other`).
  - The pop-up lists squadmates first, then "NAME (SQUAD)" from `Squad::name` (`StaticString<32>`).
  - Cells have no tooltips.
- **Buttons.** THIS UNIT and ALL UNITS sit at the top left, HIDE USED and RANDOM at the top right, flush with the grid edges (53 px in, using `lt`/`rt` aligns). RANDOM is styled orange as an action.
  - The status line between the two groups (`#dk2ml_ps_status_count` and `_used`) is set in `Refresh`: "N PORTRAITS", then "N IN USE", or "N HIDDEN" with HIDE USED on.
  - Headers read "TITLE (count)".
  - HIDE USED drops portraits anyone else wears, but keeps the trooper's own. It uses `portraits::Without`, which rebuilds the groups.
  - RANDOM applies a random unused entry from the current list, then refreshes; the picker stays open.
  - The title is "CHOOSE PORTRAIT: NAME", set with `ChangeText` on every refresh.
- **Sticky header.** When the top row is in the middle of a titled group, slot 0 shows that group's header and the rows shift down one slot.
  - `MaxTop` allows one extra row when headers exist, so the last row stays reachable.
  - `g_cellEntry` still maps every visible cell, so clicks and hover don't care.
  - `Roster::GetSquadForTrooper` returns the squad. `Squad::roster` is an inline `Roster::Trooper[]` with stride `sizeof(Roster::Trooper)` (1936), and `numInRoster` entries are filled in. The count is validated against `diedInCampaign` (the next field).
  - A trooper's name is `sHumanId::name.m_szString`.
  - Keep the cell template tooltip-less: `Item::SetTooltip` frees the item's string, so a clone sharing the template's buffer would free it twice.
- **Stock arrow bug** (from the disassembly of `Customize_OnChangePortrait`):
  1. The current index is searched only among portraits of the trooper's unit with class 0 or the trooper's class. If the trooper's `tex` isn't found, the index silently stays **0** (library entry 0, a stock Ranger portrait).
  2. The step accepts a candidate of the unit when the **current portrait's** class (not the trooper's) is 0 or matches.

  So a trooper wearing a portrait from outside its class pool falls back to index 0 (class 0) and gets "any portrait of the unit". NEXT then always lands on the unit's first portrait in load order and PREV on its last: stuck on 2–3 portraits. The Blue Vector intel submod hits this (OGA 2 troopers ending up with OGA 1 `cia*` portraits).
  - **Our replacement:** steps through `ForTrooper(trooper, ThisUnit)`, the same pool and natural order as the picker, with wrap-around. An out-of-pool portrait goes to the pool's first (NEXT) or last (PREV) entry. It applies with the picker's `Apply`.
  - It falls back to the stock code only when there's no trooper or the pool is empty.
- **Portrait pool.** `ObjectLibrary::m_humanPortraits` (`List<sHumanPortrait>`) is merged from every `human_identities` XML, including mods'. The "this unit" filter matches stock: unit hash equal, and class hash equal, or 0 only when no portrait of that unit names the trooper's class (stock rule from `human_identities.xml`: once a class has class-tagged portraits, only those are used for it). Gender 0 is male, 1 is female; mods use other values for their own pools.
